### Issue 1 — Pre-existing docs build flake from sibling worktree (Rule 3, observed but not committed)

After the first successful docs build (which proved Task 1 renders cleanly with `39 page(s) built in 2.24s`), a subsequent build invocation failed with `Cannot read properties of undefined (reading '_zod')` traced into `node_modules/zod/v4/core/schemas.js`. Investigation found:

- `apps/docs/package.json` pins `zod: ^3.25.76`, but the hoisted `node_modules/zod` at the monorepo root is `zod@4.3.6`.
- The docs workspace does not have its own `apps/docs/node_modules/zod` directory, so Astro/Starlight resolves zod@4 from the hoisted root.
- The Phase 26 decision log explicitly notes "Added zod@3 to docs workspace to isolate from monorepo zod@4 (Astro requires Zod 3 APIs)" — this is a known and resolved-in-source issue that an external concurrent install must have de-resolved.
- The failure appeared between two consecutive build runs in this plan's window. Sibling Wave-3 agents committed `283bd10` to main during this window — a strong indicator the shared `node_modules/` state was mutated by a concurrent `bun install`.

A diagnostic `bun install --cwd apps/docs zod@3.25.76` followed by `bun run --cwd packages/shared build` unblocked the docs build, which then succeeded with all my Task 2 edits in place and emitted `apps/docs/dist/reference/completions/index.html` along with the other three reference routes. The install side-effects (lockfile churn, exact-pinned zod version in `apps/docs/package.json`) were then **reverted** with `git checkout -- apps/docs/package.json bun.lockb` because:

1. The Phase 34 plan scope is documentation, not dependency management.
2. The root cause is shared-state churn from sibling worktree agents, not from my plan.
3. Touching `bun.lockb` from a parallel executor would impact every concurrent agent.
4. CI runs a fresh `bun install` on every PR, so the docs build will be green in the merge-back PR regardless of my worktree's transient state.

The fix is documented here for the orchestrator's awareness; if the post-merge CI build fails on the same `_zod` trace, the deferred action is a separate ticket to ensure `apps/docs` always carries its own resolved zod@3 (e.g., adding `apps/docs/node_modules/zod` to `bun install --frozen-lockfile` or pinning the zod version exactly in the lockfile).

The semantic correctness of my plan's MDX content is independent of this environmental issue — Task 1's first build proved the new page renders cleanly, and Task 2's recovery build (with the temporary unblock) proved all four reference routes render together.
